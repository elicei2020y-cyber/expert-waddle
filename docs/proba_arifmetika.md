# Арифметическая проба — результат разведки

**Главный вывод: модель читает пометку (59% смен), но пометка не учит
делить: спасено 1 (текст) и 4 (запрет) из 29, повреждено 1 и 3.**

Это разведка (проба), не основной прогон. `PREDICTIONS.md` этой пробой
не оценивается.

## Постановка (после двух правок)

- Модель: `Qwen/Qwen2.5-1.5B-Instruct`, float32, CPU, жадное декодирование
  (кроме принудительного обхода в В-запрет).
- Задача: по `n, M, sd, mu=4.00` вывести `df, se, t, d` — **в этом порядке**
  (исправлено с исходного `df, t, se, d`, см. «Отклонения»).
- Подсказка: системное сообщение с формулами + **3 решённых примера**
  (разные n, se, знак t, d).
- Входы: 15 отчётов с удобной арифметикой (`n` — точные квадраты,
  `se` из фиксированного набора, `sd = se·√n`, `t` — целое ±1..5,
  `M = mu + t·se`), зафиксированы в `real/proba_inputs.json` (первые 15).
- Бюджет: 3 попытки **на каждое поле отдельно** (df, se, t, d — независимо).
- Политики: А (не вмешиваться), Б (отмотка без пометки), В-текст
  (пометка в тексте, строго жадное декодирование, без обхода),
  В-запрет (пометка + принудительный обход первого генерируемого токена
  на k-й попытке, как в `igrushka/lab/model.py`).

## Фон по полям (политика А, 15 отчётов = 60 полей)

| поле | верно | % |
|---|---|---|
| df | 15/15 | 100% |
| se | 11/15 | 73% |
| **t** | **0/15** | **0%** |
| d | 5/15 | 33% |
| **итого** | **31/60** | **51.7%** |

`t` не даётся модели, даже когда нужное `se` уже верно напечатано перед
глазами (пример: отчёт 0, `se=0.40` верно, `t` напечатано `2.0` вместо
`(5.2−4.0)/0.4=3.0`). Проверка копирования: ни одно из 15 значений `t`
при А не совпало ни с одним из трёх значений `t` из примеров подсказки
(2.67, −2.00, 4.00) — 0/15 совпадений. То есть это не копирование
примера, модель действительно пытается считать и ошибается.

## Стенд: Б против А

**Расхождений 0/15 — знак в знак.** Без пометки отмотка не меняет
результат (жадное декодирование, тот же контекст) и лишь тратит
87 перепорождений впустую. Стенд исправен.

## В-текст и В-запрет

| | верно по полям (df/se/t/d) | молчание | перепорожд. | спасено | повреждено |
|---|---|---|---|---|---|
| Б | 15/11/0/5 | 15/15 | 87 | 0 | 0 |
| В-текст | 15/11/0/5 | 15/15 | 87 | **1** | **1** |
| В-запрет | 15/11/**2**/4 | 14/15 | 87 | **4** | **3** |

«Молчание» здесь означает: хотя бы одно поле не сошлось после
исчерпания своего бюджета в 3 попытки (у большинства отчётов это `t`,
которое не чинится вообще).

**Главный показатель — чтение пометки (В-текст).** На первой же попытке
после вставки пометки модель выдала значение, **отличное от значения
при А, в 17 из 29 случаев дефекта (59%)**. Первая попытка идёт с другим
текстом промпта (добавлена пометка), поэтому совпадение с А там —
не свойство жадного декодирования, а признак, что модель пометку не
учла; расхождение — признак, что учла. 59% — модель пометку в основном
читает и реагирует. Но реакция почти никогда не приводит к верному
числу: спасено всего 1 поле из 29 дефектов, и ровно 1 повреждено
(итог нулевой). В-запрет (механический перебор альтернативных первых
токенов) спасает больше (4 из 29) — не потому что «понимает» пометку
лучше, а потому что перебирает варианты грубой силой.

## Трассы

**В-запрет, отчёт 8 (n=100, M=4.4, sd=2.0) — t реально спасено:**
```
truth: t = (4.4-4.0)/0.2 = 2.00
попытка 1: [пометка: t отозвано — не сходится t=(M−mu)/se, было 0.4] → t = 1.0
попытка 2: [пометка: t отозвано — не сходится t=(M−mu)/se, было 1.0] → t = 2.0  ✓
```

**В-текст, отчёт 0 (n=81, M=5.2, sd=3.6) — модель читает пометку, но не
доходит до верного числа и застревает:**
```
truth: t = (5.2-4.0)/0.4 = 3.00
попытка 1: [пометка: было 2.0] → t = 1.4  (сменила)
попытка 2: [пометка: было 1.4] → t = 1.4  (повторила — застряла)
попытка 3: [пометка: было 1.4] → t = 1.4  (повторила)
```

**В-запрет, отчёт 0 — механический перебор без сходимости, попутно
портит верное поле:**
```
t:  2.0 → 0.0 → 4.0 → 2.0   (вернулась к исходному, бюджет исчерпан, t неверно)
d:  0.44(было неверно и при А) → 1.44 → 2.0 → 3.0  (осталось неверно)
```
Уточнение по этому примеру (найдена и исправлена ошибка в тексте
предыдущего устного отчёта, не в коде): ранее `d=0.4`, стартовое
значение d внутри трассы В-запрета, было ошибочно названо «верным при
А». Прямая проверка кода `legit_d` на этом отчёте (`M=5.2, sd=3.6,
n=81`) показывает: `legit_d(0.4)=False` и `legit_d(0.44)=False` —
законный путь `(M−mu)/sd=0.3333`, оба значения вне допуска 0.005.
При А `d` в этом отчёте было `0.44` и уже отмечено неверным (`correct.d
= False`). Проверка (`legit_d`) верна, баг не найден, таблицы выше
пересчёта не требуют.

## Секунды на отчёт

А — 15.58 с; Б — 38.80 с; В-текст — 40.74 с; В-запрет — 41.25 с.

## Отклонения от ZADANIE.md (сводно, по всей арифметической линии)

1. Порядок полей `df, se, t, d` вместо `df, t, se, d` — устраняет
   структурный дефект: в исходном порядке `t` печатался раньше `se`,
   был невычислим и не спасаем отмоткой (см. предыдущий отчёт, гейт
   0.5B и 1.5B при старом порядке — 20% и 47.5%).
2. Следствие: опоздание обнаружения дефекта пропадает — «отмотка на
   одно поле» и «отмотка к происхождению по графу» совпадают. Политика
   Г не запускалась. **В `PREDICTIONS.md` П4 не оценивается — постановка
   изменена** (сам файл не редактировался).
3. Подсказка: 3 примера вместо одного.
4. Модель: `Qwen2.5-1.5B-Instruct` вместо 0.5B (по критерию этапа 0б).
5. Бюджет: на поле (3 попытки на df/se/t/d независимо), а не общий
   бюджет на отчёт.
6. Пометка расщеплена на В-текст (без обхода) и В-запрет (с обходом).
7. Входы — не по Лайкерту, как в основном ZADANIE (n от 8 до 200
   произвольно), а «удобная арифметика» (точные квадраты n, круглые se)
   — специально для этой разведки, чтобы у отмотки было что спасать.
